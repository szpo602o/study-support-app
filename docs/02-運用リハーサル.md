# 運用リハーサル（実装前・1〜2週間）

アプリを書く前に、日次・週次の操作量が現実的かを紙またはスプレッドシートで確認する。

## 目的

- 日次1分・週次10分が守れるか
- 「当初計画を消さず残す」運用がプレッシャーとして機能するか／アプリを開かなくなるか
- ロードマップ → 中間目標 → 週間タスクの分解が自分の教材に合うか

## 準備（初回30分以内）

1. アクティブ目標を最大2つ書く（試験日付き）
2. 各大目標にロードマップを5〜10段階で書く（各段階に目標日）
3. 各大目標で「今フォーカスする中間目標」を1つ選ぶ（期限は2週間以内）
4. 今週のタスクを約5件書き、各タスクに想定時間を付ける

## 毎日（1分）

| 日付 | 時間区分 | 取り組んだタスク | 完了にしたタスク | 入力タイミング（当日／後日） |
|------|----------|------------------|------------------|------------------------------|
|      |          |                  |                  |                              |

時間区分: `0` / `1〜14` / `15〜29` / `30〜59` / `60〜119` / `120+`

ルール:

- 0分の日も行を残す
- 当週内の後日入力は可。その場合「後日」と書く
- 進捗率は書かない

## 毎週（日曜夜・10分）

### A. 結果の記録（消さない）

| 項目 | 記入例 |
|------|--------|
| 週 | 2026-W32（月〜日） |
| 当初タスク数 | 5 |
| 完了数（当初のみ） | 3 |
| 途中追加 | 1件（完了1） |
| 想定時間合計 | 8時間相当 |
| 完了タスクの想定時間合計 | 5時間相当 |
| 実績時間（区分の概算合計） | 約6時間 |
| 計画変更 | 2件 |

### B. 未完了タスク

| タスク | 未達理由 | 処遇 |
|--------|----------|------|
|        | 時間不足／見積もり過大／優先度変更／着手を避けた／その他 | 来週もやる／延期／やめる |

### C. 翌週計画

| タスク | 想定時間 | 由来（新規／再コミット） |
|--------|----------|--------------------------|
|        |          |                          |

### D. 中間目標チェック

| 項目 | 記入 |
|------|------|
| 中間目標 | |
| 目標日 | |
| 状態 | 進行中／遅延中／完了 |
| 遅延時の決断 | 取り戻す／期限変更／範囲縮小／該当なし |

週を「確定」したら、その週の行は書き換えない。

## 判定（1〜2週間後）

次をすべて Yes なら、MVP実装に進んでよい。

| 確認項目 | Yes/No |
|----------|--------|
| 日次入力をほぼ毎日、1分以内で終えられた | |
| 日曜のレビュー＋翌週計画を10分以内で終えられた | |
| 「当初計画を残す」ことに耐えられた（アプリ／表を避けなかった） | |
| ロードマップと中間目標の粒度が無理なく使えた | |
| 通知なしでも、表を開くきっかけを自分で持てた（またはリマインダが欲しいと分かった） | |

No がある場合は、実装前に仕様側（入力項目・週次手順）を削る。

## 卒業制作の成功基準との関係

このリハーサルは「実装に進む可否」の確認。  
卒業制作の成功基準は、実装後に **4週間** 一連フローを継続できたかで別途判定する。
